# Nebi-in-JupyterLab screenshot/video capture pipeline

**Doc it feeds:** `docs/src/content/docs/nebi-in-jupyterlab.md`
**Reference:** developer-role user stories in https://github.com/nebari-dev/nebi/pull/425

## Problem

`nebi-in-jupyterlab.md` documents the CLI/kernel-picker/web-UI workflows a
developer runs day to day, but it's text-and-code-block only. We want real
screenshots (and one short video for the one workflow that genuinely spans
two sessions) embedded in the page, generated by driving the real thing with
Playwright rather than hand-mocked.

## Scope

Captured, driven for real:

- `nebi init` / `pixi add` / `nebi shell` / `nebi run` (terminal)
- Kernel picker showing a workspace as a notebook kernel, including the
  actionable stub-kernel error for an uninstalled/not-pulled workspace
- `nebi push` (as one user) → `nebi pull` + `nebi workspace install` (as a
  second user) — the one workflow recorded as video, since a screenshot can't
  show the handoff between two sessions
- `nebi diff` / `nebi workspace tags`
- Cleanup: `nebi workspace uninstall` / `remove` / `prune`
- The nebi server's own web UI: workspace list, share dialog (granting the
  second user access), version history/rollback

**Explicitly out of scope** (needs a real JupyterHub, not just JupyterLab):
the jhub-apps environment-picker workflow and the hub-level pinned Nebi
service card. Those two doc sections stay text-only until/unless it's worth
standing up a real Hub for them.

## Why no Kubernetes

The repo's own local dev loop (`make up` / Tiltfile) deploys with
`nebariapp.enabled=false` and no Keycloak/Nebi server — it only gives a bare
JupyterHub with dummy auth, so it can't demonstrate push/pull, the web UI, or
a real login. Standing up Keycloak + `nebari-nebi-pack` + JupyterHub to get
the rest would mean a k3d cluster, Helm, and considerably more moving parts
just to produce documentation screenshots. Since the workflows in scope only
need a `nebi` server plus plain JupyterLab, the pipeline runs both as local
processes/containers instead — no cluster, no Helm.

## Architecture

A new `docs/scripts/capture/` directory holding a Node orchestrator
(`run.mjs`), invoked as `npm run capture` from `docs/`. It builds/starts the
minimal stack, drives Playwright through each workflow, writes assets to
`docs/src/assets/nebi-jupyterlab/`, and always tears the stack down.

```
docs/
  scripts/capture/
    run.mjs                 # orchestrator: build/start/capture/teardown
    log.mjs                 # prefixed real-time log multiplexer
    steps/
      init-shell-run.mjs
      kernel-picker.mjs
      share-workflow.mjs
      diff.mjs
      cleanup.mjs
      web-ui.mjs
  src/assets/nebi-jupyterlab/
    01-init-terminal.png
    02-kernel-picker.png
    03-stub-kernel-error.png
    04-push-pull-handoff.webm
    05-diff-output.png
    06-cleanup.png
    07-webui-workspace-list.png
    08-webui-share-dialog.png
```

## Components

1. **Nebi server harness** — builds the `nebi` binary from `~/work/nebi` (or
   accepts a pinned version via env var, matching how `images/Dockerfile`
   resolves `NEBI_IMAGE`/`NEBI_VERSION`), runs `nebi serve` as a background
   process with basic auth and a throwaway SQLite file in a temp dir.
   Bootstraps two users, `alice` and `bob`, and obtains a token for each —
   the exact bootstrap mechanics (CLI flag vs. first-run admin seeding) get
   nailed down against `cmd/nebi/serve.go`/`login.go` during implementation.
2. **Two JupyterLab containers** — two `docker run` invocations of the image
   built by `make jupyterlab`, ports 8888/8889, container names
   `nebi-docs-alice`/`nebi-docs-bob`, each with `NEBI_REMOTE_URL` pointing at
   the host's nebi server and that user's token as `NEBI_AUTH_TOKEN`, and
   `--ServerApp.token=""` so Playwright never has to handle a login screen.
3. **Playwright capture steps** — one module per doc section, run in doc
   order against whichever container(s) that section needs (see Scope
   above for the list).
4. **Doc embedding** — images/video added inline in `nebi-in-jupyterlab.md`
   at the matching step. Assets are committed to git like any other doc
   asset — this is a run-locally/review/commit model, not CI-generated.

## Observability (hard requirement)

Nothing about this pipeline is allowed to go quiet while it works, and
nothing is allowed to sit on a long timeout hoping something eventually
happens:

- **Every child process's real output streams live**, prefixed by source,
  merged into the orchestrator's own stdout as it happens — never buffered
  and dumped only at the end or on failure. `nebi serve`'s stdout/stderr,
  and both containers' `docker logs -f`, all stream concurrently through
  `log.mjs` with `[nebi]` / `[alice]` / `[bob]` prefixes.
- **Every Playwright step logs immediately before and after** each real
  action (`→ opening kernel picker...` / `✓ kernel picker open`), so a hang
  is visible at the exact action it's stuck on, not inferred after the fact.
- **All waits are short-interval polls with a hard cap, not sleeps.** Health
  checks (nebi `/health`, each container's Jupyter `/api`) poll every 1–2s
  and fail fast (≤15–20s cap) with a specific error naming what never came
  up — never Playwright's long default action/navigation timeouts. Playwright
  itself is configured with a short (~8s) action/navigation timeout so a
  stuck page load surfaces in seconds, not close to a minute.
- **Failures are specific.** A capped wait or failed step reports which
  component and which check failed, not a generic "timed out."

## Data flow

`npm run capture` → `run.mjs`:

1. Preflight — fail fast if `docker`/`go` aren't on `PATH`.
2. Idempotent start — stop/remove any leftover containers or process from a
   prior crashed run before starting fresh.
3. Build the nebi binary → start `nebi serve` → poll `/health` (short
   interval, capped).
4. Bootstrap alice/bob, grab tokens.
5. `docker run` both JupyterLab containers → poll each one's `/api`
   (short interval, capped).
6. Launch Playwright, run each capture step module in doc order, streaming
   logs throughout (see Observability).
7. **Always** (success or failure, via try/finally): stop both containers,
   stop the nebi server process, clean temp dirs.
8. Print a summary of what was written — or exactly what failed.

## Error handling

Every capture step runs inside a try/finally at the orchestrator level, so a
failure partway through never leaves docker containers or the nebi server
process running in the background. If a step fails, the script names which
step and which underlying action failed and exits non-zero — it does not
silently skip ahead and produce a partial, misleadingly-labeled asset set.

## Verification

This is an asset generator, not something to unit test. "Done" means: run
`npm run capture`, watch the real-time logs to confirm each step actually
did what it claims, eyeball the resulting PNGs/video for correctness,
confirm `npm run build` still succeeds with the new images embedded and
`scripts/check-links.sh` still passes, then commit the assets alongside the
doc changes.

## Rejected alternatives

- **Bare `pixi run jupyter lab` on the host instead of the Docker image:**
  `images/jupyterlab/pixi.lock` targets Linux and won't solve/run natively
  on macOS, and it would mean hand-reproducing the `nebi` binary +
  `jupyter_server_config.py` wiring that the Dockerfile already assembles.
- **Standing up Keycloak + `nebari-nebi-pack` + JupyterHub in a local k3d
  cluster** to get full coverage including jhub-apps: rejected per the "Why
  no Kubernetes" section — disproportionate infrastructure for documentation
  screenshots. Revisit only if the jhub-apps/hub-card sections are judged
  worth it later.
- **Static hand-built mock of the jhub-apps environment picker:** would give
  a visual without real infra, but isn't driven by real app behavior and
  could go stale silently if the actual UI changes. Rejected in favor of
  leaving those two sections text-only for now.
- **CI-integrated regeneration (GitHub Actions job building/running the
  nebi binary and JupyterLab containers):** more reproducible for other
  contributors, but hands the docs CI pipeline ownership of running a Go
  binary and Docker containers just to keep screenshots fresh. Rejected in
  favor of a manual local script whose output is reviewed and committed.

## Out of scope

- jhub-apps environment-picker workflow and the hub-level pinned Nebi card
  (see Scope).
- CI integration (see Rejected alternatives).
- Any change to the `nebi` binary, `nebari-nebi-pack`, or the chart itself —
  this pipeline only consumes existing, already-wired images/binaries.
